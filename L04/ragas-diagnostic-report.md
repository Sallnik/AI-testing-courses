# RAGAS Diagnostic Report — шаблон

**Додатковий матеріал до заняття 4 «RAG: три точки відмови».**

Це порожня форма для ДЗ_3. Ви заповнюєте її даними PayPilot: записами з лабораторної і прогонами, які доміряєте в ДЗ. Біля кожного розділу вказано, де в темі розібрано те, що туди треба вписати. Після курсу той самий шаблон підходить для RAG-системи вашої команди.

Обсяг — до двох сторінок: шість розділів і останній рядок. Розділи 1–6 відповідають крокам 1–6 ДЗ. Retrieval-кейси (крок 7) ви дописуєте в `golden.jsonl`, тому окремого розділу для них немає.

Документом рішення звіт роблять три речі:

- кожне твердження про точку відмови спирається на **retrieval-контекст**, а не на текст відповіді;
- для кожного виправлення названо **ціну** і те, що від нього псується;
- останній рядок відповідає на питання «що обміняли · чого не робимо · за яких умов рішення зміниться».

**Як рахувати метрики** (так само, як у таблиці «Три метрики на прикладах лабораторної»):

| Метрика | Що рахуєте | Знаменник |
|---|---|---|
| context recall | скільки фактів з еталона дійшло до моделі | факти еталона |
| context precision | скільки з принесених фрагментів справді потрібні | усі принесені фрагменти |
| faithfulness | скільки тверджень відповіді є в принесеному | твердження з відповіді |

Біля кожного числа показуйте рахунок: `1 з 2 = 0.5`. Якщо пошуку не було, ставте «—» і пояснюйте чому.

## 2. Локалізація

*Крок 2 ДЗ. У темі: «Три точки відмови і доказ», «Таблиця симптомів», «Retrieval-контекст як доказ». Дані: вправи 1–4 лабораторної, скарги C-13 і C-14.*

Правило з теми: перш ніж називати шар, відкрийте retrieval-контекст. У колонці «Доказ» — ідентифікатор фрагмента й уривок тексту, наприклад `tariffs.md#b3 — «… | Tier 3 | 0.5% | EUR 5»`. Якщо агент не шукав, доказом є відсутність спана `tool.search_knowledge_base` у трейсі. Текст відповіді доказом не вважається: симптоми різних точок збігаються.

| Випадок | Симптом | Точка відмови | Доказ (retrieval-контекст) |
|---|---|---|---|
| Вправа 1 | не знайшов, приніс половину | індексація | fragment id: tariffs.md#b3 "austed. / Tier / FX spread / Free monthly conversion allowance / /---/---/---/ / Tier 1 / 1.5% / EUR 500 / / Tier 2 / 0.9% / EUR 1,000 / / Tier 3 / 0.5% / EUR 5" |
| Вправа 2 | не знайшов, приніс половину | видача | коли top_k=4 не знаходить фрагмент limits.md#s1 |
| Вправа 3 (D25) | вхід правильний, відповідь хибна | генерація | результат виконнання інструменту tool.quote_fx - однаковий як для випадку з дефектом так і без нього. |
| Вправа 4 (D05) | агент не шукав | генерація | не відбувся пошук по корпусу |
| C-13 | не знайшов, приніс половину | індексація | Але агент приносить отріщану таблицю і баг що для tier3 чат виводить 1500 EUR - не відтворюється: fragment id: tariffs.md#b3 "austed. / Tier / FX spread / Free monthly conversion allowance / /---/---/---/ / Tier 1 / 1.5% / EUR 500 / / Tier 2 / 0.9% / EUR 1,000 / / Tier 3 / 0.5% / EUR 5" |
| C-14 | знайшов шматок без умов | індексація | Чанки чомусь називаються по-різному (clean: disputes.md#s1 lesson-04: disputes.md#b1), але текст у них починаютсья однаково: # Payment dispute rules ## Reason codes and chargeback windows Each reason code has a window in days from the transaction date. A dispute opened after the windo|

Симптом — з таблиці симптомів теми і лабораторної: знайшов шматок без умов / не знайшов, приніс половину / приніс зайве / вхід правильний, відповідь хибна / агент не шукав.
Точка відмови: індексація / видача / генерація. Скарга, яка не відтворилася з двох спроб, — «не відтворюється».

**Розподіл:** індексація ... · видача ... · генерація ... · не відтворюється ...

Якщо всі випадки припали на одну точку, перевірте, чи не класифікували ви їх за текстом відповіді.

## 3. Доказ причини

*Крок 3 ДЗ. У темі: «D16: чанкінг ріже тарифну таблицю». Дані: порівняння з кінця вправи 1.*

```
запит    Search the Verta documentation: what FX spread applies to my account and what is my free monthly conversion    allowance?
клієнт   CUS-0003
профіль  clean
top_k    1
```

| Метрика | `kb_clean` | `kb_broken` | Дельта |
|---|---|---|---|
| context recall | 1 | 0.5 | -0.5 |
| context precision | 1 | 1 | 0 |
| faithfulness | 1 | 1 | 0 |

**Якщо вважати що нам потрібна додаткова інформація про умови накладанея спред 0.5 - то ситуація буде трішки іншою. Але це коштуватиме більше токенів і юзер цього не питав, тому це питання повиинне виріщуватись на продакт рівні.**

| Метрика | `kb_clean` | `kb_broken` | Дельта |
|---|---|---|---|
| context recall | 0.5 | 0.33 | -0.17 |
| context precision | 1 | 1 | 0 |
| faithfulness | 1 | 1 | 0 |

**Що лишалося незмінним:** профіль, промпт, модель, `top_k`, клієнт, запит. Порівняння доводить причину, лише коли між прогонами змінилася одна річ — індекс. Профіль `lesson-04` для цієї пари не підходить: він змінює одразу індекс, `top_k` і промпт.

**Висновок одним реченням:** На поломаній індексації ми не отримуємо корректної суми чи не отримуємо її взагалі. Це ламає наш: context recall. З двох наведених таблиць вище видно що context recall може змінюватись в залежності від вимог замовника.

## 4. Зворотний випадок

*Крок 4 ДЗ. У темі: «Коли контекст цілий, а відповідь хибна». Дані: вправи 3 і 4.*

Прогін, де вхідні дані правильні, а відповідь хибна. Без цього розділу на retrieval-шар легко списати всі збої.

```
дефект                          D25
профіль / клієнт                clean / CUS-0005
спан пошуку                     є / немає
final_amount з tool.quote_fx    6463.043478
підсумок у відповіді            6 500
правило, яке додав D25          Доданий System Prompt який змушує округлувати суму до цілої сотні(«Чим відрізняється від clean →»)
хибний підсумок                 5 з 5 прогонів  (кнопка «×5»)
```

**Чому recall, precision і faithfulness тут не рахуються:** Чому не recall, precision: тому що ми не шукали в корпусі, а відповідали відповідно до результату тулів. Чому не faithfulness: тому що агент чесно згкнерував те що прийшло у retrieval + застосував правило округлеггя додане до system prompt

**Як доведено, що збій стався в генерації:** Тому що інструмент повернули на корректну відповідь у retrieval

**Контроль D05 (вправа 4):** спан пошуку: немає · відповідь агента EUR 15,00 · правильна відповідь з документації 15.00 + 0.3%

## 6. Рішення й межі

*Крок 6 ДЗ. У темі: «Ціна виправлення: що промптом не лікується», «Чого локалізація не ловить».*

Таблиця має ту саму будову, що в розділі «Ціна виправлення», але заповнюєте її для реальної системи, а не для стенду.

| Точка | Чим лагодиться | Що це коштує в реальній системі | Що псується натомість | Промпт допоможе? |
|---|---|---|---|---|
| Індексація | речанкінг - перреіндексація | не можу відповісти бз вхіжних даних | є імовірність "поламати" інші чанки | ні |
| Видача | збільшенням або зменшенням top_k, корректним ранжуванням чанків | більша витрата токені при збільшенні top_k | при зміні top_k інші запити можуть недооотримати або отримати забагато фрагментів | ні |
| Генерація | зміною у промпті, рушії | робочі години того хто править промпт | іншій кейси після змінм промпта | так |

**Вартість однієї переіндексації в реальній системі:** обсяг корпусу ..., час ..., гроші .... Припущення: ...

**Що промптом не лікується:** Генерація

**Залишковий ризик.** Щонайменше один клас збоїв, який проходить recall, precision і faithfulness одночасно. Приклад такого класу розібрано в розділі «Чого локалізація не ловить». Формат рядка той самий, що на L03:

```
що не покрито                    Answer Revelancy/Hallucination/Domain Correctness (Ми запитали про спред під час ковертацію валют, а в retieval прийшла наша остання транзакція) 
що станеться, якщо зламається    Відповідь буде не корректною
чому живемо з цим зараз          так, бо клієнт не нестиме фінансових хбитків при не крректній відповіді
відкласти / прийняти             прийняти
```

**Джерело еталону.** Recall рахується проти еталона, який визначили ви. Неповний еталон дає зелений recall на неповному retrieval-контексті. Назвіть, звідки ви брали еталон для звіту і `reference` для кейсів.
